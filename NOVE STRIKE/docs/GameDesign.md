# NOVE STRIKE ゲーム設計書

本書は NOVE STRIKE の全体仕様を定める。実装はすべて本書を基準に進める。
本書と実装が食い違った場合は、実装を修正するか本書を改訂するかを判断し、放置しない。

- 最終更新: 2026-09-04
- 関連文書: [実装ロードマップ](Roadmap.md) / [開発規約](../CLAUDE.md)

## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| タイトル | NOVE STRIKE |
| ジャンル | トップダウン視点 3D ローグライト・シューター |
| プラットフォーム | PC（キーボード＋マウス／ゲームパッド対応） |
| 目的 | **ポートフォリオ作品** |
| 期限 | なし（品質優先） |
| Unity | 6000.5.3f1 / URP 17.5.0 |

### 1.1 コンセプト

SF 施設を舞台に、部屋を踏破しながら装備と能力を組み上げ、最深部のボスを倒す。
1 ラン 5〜10 分で完結し、失敗しても新武器と強化項目が解放されて次のランに引き継がれる。

### 1.2 評価軸（ポートフォリオとしての優先順位）

ポートフォリオでは「機能の多さ」より **設計の一貫性と、一通り遊べる完成度** が評価される。
判断に迷った場合は次の順で優先する。

1. **ラン 1 周が最後まで破綻なく遊べること**
2. **設計の一貫性**（Model / Presenter / Behavior 分離を崩さない）
3. **手触りの良さ**（射撃・ダッシュのレスポンス）
4. 機能の数

## 2. ゲームループ

### 2.1 全体構造

```
タイトル
  └─ ラン開始
       ├─ 部屋 1（戦闘）→ クリア報酬で強化を 3 択から 1 つ選択
       ├─ 部屋 2（戦闘）→ 〃
       ├─ 宝箱部屋 / 休憩部屋      ← 戦闘部屋の合間に配置
       ├─ …（部屋 8〜12）
       └─ ボス部屋 → 撃破でラン成功
  └─ ラン終了（成功 / 失敗）
       └─ 永続アンロックの解放判定 → タイトルへ
```

### 2.2 ラン構造

- **部屋探索型フロア制**。1 フロアで完結する。
- 1 ランあたりの部屋数: **8〜12**
- 想定プレイ時間: **5〜10 分**
- プレイヤーは部屋をクリアすると次の部屋へ進める。**後戻りは不可**（進行管理を単純化するため）。

### 2.3 部屋の種類

| 種類 | 内容 | 出現数の目安 |
| --- | --- | --- |
| 戦闘部屋 | 敵を全滅させるとクリア。クリア報酬で強化 3 択。 | 6〜9 |
| 宝箱部屋 | 戦闘なし。宝箱から強化またはリソースを入手。 | 1〜2 |
| 休憩部屋 | 戦闘なし。HP 回復。 | 1 |
| ボス部屋 | ボス 1 体。撃破でラン成功。 | 1（最後） |

## 3. 部屋・フロア生成

### 3.1 方式

**手作り部屋プレハブ ＋ 内部要素のランダム化**

- 部屋の**形状・壁・出入口は手作りのプレハブ**として複数用意する。導入済みの 3D Scifi Kit を用いて見た目の品質を担保する。
- 部屋の**中身はランダム化**する。ランダム化の対象は以下。
  - 敵の種類と数、湧き位置
  - 障害物・遮蔽物の配置
  - 宝箱の有無と中身

### 3.2 生成手順

1. フロア構成テーブルから、部屋の並び（種類の列）を決定する。
2. 各部屋に対し、その種類に対応する部屋プレハブ候補からランダムに 1 つ選ぶ。
3. 選ばれた部屋プレハブ内の **スポーンポイント** に、抽選した敵・障害物・宝箱を配置する。
4. ボス部屋は固定プレハブとし、抽選対象から除外する。

### 3.3 設計方針

- 部屋プレハブは **スポーンポイントを子オブジェクトとして保持**し、生成側はそれを参照するだけにする。部屋の見た目と生成ロジックを分離する。
- 抽選テーブルは ScriptableObject（`RoomData` / `FloorData`）で持ち、コードに数値を埋め込まない。既存の `EnemyData` / `EnemyDatabase` と同じ方針とする。

## 4. 戦闘

### 4.1 プレイヤーの行動

| 行動 | 内容 |
| --- | --- |
| 移動 | 8 方向移動。既存 `PlayerController` を踏襲。 |
| 射撃 | マウス／右スティック方向へ射撃。既存 `Bullet` / `BulletPool` / `FirePoint` を使用。 |
| ダッシュ | 短距離の高速移動。**無敵時間あり**。クールダウンあり。 |
| 武器切替 | 所持している武器を切り替える。 |

### 4.2 ダッシュ仕様

- 回避の主軸となる行動。弾幕を抜ける気持ちよさを担保する。
- **無敵時間**をダッシュ中に付与する。無敵時間・移動距離・クールダウンはすべて ScriptableObject で調整可能にする。
- ダッシュ中は射撃不可とする（強すぎる行動にしないため）。

### 4.3 武器

- プレイヤーは複数の武器を所持し、切り替えて戦う。**同時所持数は 2**（切替の判断を意味のあるものにするため）。
- 武器はデータ駆動とする。既存の `BulletData` / `WesponMagazineModel` を拡張する。
- 武器ごとに定義する項目: 攻撃力 / 連射速度 / 弾速 / 弾数 / リロード時間 / 弾の挙動

### 4.4 敵

- 種類数: **4〜5 種**（ボスを除く）
- 既存の `IEnemyMoveBehavior` / `IEnemyAttackBehavior` の組み合わせで表現する。**新しい敵を追加するときにクラスを増やさず、データとビヘイビアの組み合わせで作れる状態を維持する。**

| # | 想定する敵 | 移動 | 攻撃 |
| --- | --- | --- | --- |
| 1 | 突撃型 | 追跡 | 自爆 |
| 2 | 射撃型 | 一定距離を保つ | 単発射撃 |
| 3 | 砲台型 | 静止 | 単発射撃 |
| 4 | 高速型 | 高速追跡 | 接触ダメージ |
| 5 | （予備） | 未定 | 未定 |

- ボスは 1 体。複数の攻撃パターンを持ち、HP 帯によってパターンが変化する。

## 5. 強化とアンロック

### 5.1 ラン中の強化（ラン限り・持ち越さない）

入手経路は 3 つ。**実装優先度は下表の順**とする（第 8 章の整合性リスクに対応）。

| 優先 | 経路 | 内容 |
| --- | --- | --- |
| **1** | 部屋クリア報酬 | 戦闘部屋クリア時に強化 3 つが提示され、1 つ選ぶ。**本作の中核**。 |
| 2 | 宝箱・ドロップ | 宝箱部屋の宝箱、敵のドロップから入手する。 |
| 3 | レベルアップ選択 | 経験値を溜めてレベルアップし、その場で能力を選ぶ。 |

- 強化はスタックする（同じ強化を複数回取れる）ものと、一度しか取れないものを分ける。
- 強化もデータ駆動とし、ScriptableObject で定義する。

### 5.2 永続アンロック（ラン間で持ち越す）

**ハイブリッド方式**。能力強化はラン限りだが、以下は永続する。

| 対象 | 内容 |
| --- | --- |
| **新武器のアンロック** | 条件を満たすと、ラン中に出現する武器プールに新しい武器が加わる。 |
| **強化項目の解放** | 条件を満たすと、ラン中に提示される強化の種類が増える。 |

- 解放条件はランの結果（到達部屋数、ボス撃破、累計撃破数など）に紐づける。
- **セーブデータが必要**。`Application.persistentDataPath` に JSON で保存する。

## 8. スコープと整合性リスク

### 8.1 完成の定義

以下をすべて満たした時点で「完成」とする。

- [ ] 1 フロア（部屋 8〜12）＋ボス 1 体を通しでプレイできる
- [ ] 敵 4〜5 種が実装され、それぞれ異なる立ち回りを要求する
- [ ] 射撃・ダッシュ・武器切替が機能し、手触りが破綻していない
- [ ] 部屋クリア報酬による強化選択が機能する
- [ ] 永続アンロック（新武器・強化項目）が保存・復元される
- [ ] タイトル → ラン → リザルト → タイトルの循環が成立する

### 8.2 認識しているリスク

**スコープは「小規模」だが、機能構成は小規模の枠に対して厚い。**
戦闘は最も厚い構成（射撃＋ダッシュ＋武器切替）、強化入手は 3 経路すべてを採用している。
このままだと「機能は揃っているがバランス調整が浅い」状態になりやすい。

**対応方針**

- 強化入手は 5.1 の優先度に従い、**「部屋クリア報酬」を最優先で完成させる。**
- 残る 2 経路（宝箱・ドロップ／レベルアップ）は、中核が完成し、バランスが破綻していないことを確認してから着手する。
- 期限がないため、**機能を増やす前に既存機能の手触りを詰める**ことを優先する。

## 9. 技術方針

### 9.1 アーキテクチャ

既存の分離方針を維持する。**新規実装でこの構造を崩さない。**

| 層 | 役割 | 既存の例 |
| --- | --- | --- |
| Scene | シーン単位の進行管理 | `AppMain` / `GameSceneManager` / `SceneBase` / `TitleScene` / `BattleScene` |
| System | ゲーム進行のシステム | `Battlesystem` / `EnemyManager` / `PlayerManager` |
| Controller (View) | MonoBehaviour。入力受付と描画・物理の実行 | `CharaBase` / `PlayerController` / `EnemyController` |
| Presenter | 判断と制御。MonoBehaviour ではない | `EnemyAIPresenter` / `PlayerCombatPresenter` |
| Model | 状態の保持 | `CharaStatusModel` / `PlayerStatus` / `EnemyStatus` |
| Behavior | 差し替え可能な振る舞い | `IEnemyMoveBehavior` / `IEnemyAttackBehavior` |
| Data | ScriptableObject 等のデータ資産 | `EnemyData` / `EnemyDatabase` / `BulletData` |

### 9.2 実装ルール

- **数値をコードに埋め込まない。** バランス値はすべて ScriptableObject に置く。
- **新しい敵・武器・強化を追加するときにクラスを増やさない。** データとビヘイビアの組み合わせで表現する。
- 生成コストの高いオブジェクト（弾・敵・エフェクト）は**プーリングする**。既存 `BulletPool` の方式を踏襲する。
- 更新は Tick 駆動を維持する（既存の `TickUpdate` / `TickFixedUpdate`）。個々の MonoBehaviour が勝手に `Update` を持たない。

### 9.3 制約

- 既存 `.cs` は **Shift_JIS (CP932) / BOM なし**。編集時にエンコーディングを変えない（規約 5.3）。
- 命名は `m_` プレフィックス（フィールド）／ `arg_` プレフィックス（引数）を維持する（規約 5.4）。
